# Error codes

Two distinct error surfaces. JSON-RPC `error.code` numbers are returned with HTTP 200 and a standard JSON-RPC envelope. x402 `reason` strings ride on the body of an HTTP 402 response (no JSON-RPC envelope).

## JSON-RPC errors

| Code     | Symbol             | Meaning                                                                                                                                                                                                                         | Recovery                                                                                                                                              |
| -------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-32700` | `PARSE_ERROR`      | Request body was missing or could not be parsed as JSON.                                                                                                                                                                        | Send a valid JSON body. (See platform note on [JSON-RPC](/docs/json-rpc) — Firebase intercepts malformed JSON when `Content-Type: application/json`.) |
| `-32600` | `INVALID_REQUEST`  | Body parsed but is not a valid JSON-RPC envelope: missing `jsonrpc: "2.0"`, missing `method`, or `id` of the wrong type. Also returned for HTTP methods other than POST on `/rpc`.                                              | Fix the envelope. Always send `{ "jsonrpc": "2.0", "id": <id>, "method": <name>, "params": <obj> }`.                                                  |
| `-32601` | `METHOD_NOT_FOUND` | The `method` field did not match a registered handler.                                                                                                                                                                          | Call `listReportTypes`, `reviewSample`, or `reviewFull`. Discover the available methods by fetching `/.well-known/agent.json`.                        |
| `-32602` | `INVALID_PARAMS`   | Params failed validation. Specific messages: `"params must be an object"`, `"params.code must be a non-empty string"`, `"params.reportType must be one of the supported report types — call listReportTypes to discover them"`. | Fix the params. The `message` field always tells you which field is wrong.                                                                            |
| `-32603` | `INTERNAL_ERROR`   | Any uncaught exception inside a handler. The `message` field carries the underlying error string. Common causes: Gemini API key missing or invalid, model timeout.                                                              | Retry once. If it persists, check that `GOOGLE_AI_API_KEY` is set on the deployment.                                                                  |

## x402 reasons (in HTTP 402 body)

The 402 body is shaped `X402Quote & { reason?: string }`. The `reason` is set whenever a previous payment attempt failed, and is purely informational — the client should always treat the _quote_ itself (`amount`, `recipient`, `expiresAt`, `nonce`) as the source of truth for the next attempt.

| `reason`                   | Meaning                                                                                                                                                                                          | Recovery                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `X-Payment header missing` | First call, no payment supplied yet.                                                                                                                                                             | Sign the transaction; retry with `X-Payment: <signature>`.                                                         |
| `tx not confirmed`         | The agent's RPC could not see the transaction at `confirmed` commitment even after 6 retries (~9 seconds total). Usually means devnet RPC propagation lag, or you submitted the wrong signature. | Wait 5–10 seconds and retry the same `X-Payment` value. If still failing after 30 seconds, send a new transaction. |
| `tx is not a SOL transfer` | The transaction has no `SystemProgram.transfer` instruction (e.g. it was a token transfer or program call).                                                                                      | Build a plain `SystemProgram.transfer` instruction. See [Payment handshake](/docs/payment-handshake).              |
| `recipient mismatch`       | Transfer's `toPubkey` is not the agent's wallet (`2vCfh5Cia6iwb7uBfrWeXaG6UtvTzV6kzzH5XCfAVmZp`).                                                                                                | Use the `recipient` field from the latest 402 quote. Do not hard-code it from old docs.                            |
| `amount too low`           | Transfer's lamports are less than `1_000_000`.                                                                                                                                                   | Use the `amount` field from the latest 402 quote. Overpaying is fine.                                              |
| `tx is stale`              | Transaction's `blockTime` is older than 5 minutes.                                                                                                                                               | Send a new transaction. The signature cannot be revived.                                                           |
| `payment already consumed` | Verification succeeded, but this signature has already been claimed for a previous successful call. Replay protection caught it.                                                                 | Send a new transaction for a new call. Each signature is good for one call.                                        |

## How to surface errors in a client

- For JSON-RPC errors, branch on `response.error.code`. Recoverable codes are `-32602` (fix params) and `-32603` (retry once). `-32600` and `-32601` are programmer errors and should be logged loudly.
- For x402, branch on HTTP status. A `402` is always recoverable: read the `reason`, optionally show it to the user, and act according to the table above. Use the quote's `recipient` and `amount` for the next attempt.
- Always include the response body in error logs — both surfaces are designed to be self-describing.
